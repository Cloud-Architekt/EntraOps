# Migration guide for EntraOps 0.x GitHub deployments

Use this guide when your existing private GitHub repository already runs an EntraOps 0.x deployment.
Upgrade that repository in place. Do **not** create a new repository from the GitHub template and do
**not** run the new-deployment setup against a second repository: doing so creates a separate
workload identity and an empty data history while leaving the current deployment behind.

> [!NOTE]
> Running EntraOps 1.0? Follow [Upgrade from EntraOps 1.0 to 1.1](#upgrade-from-1-0) instead of the
> 0.x steps below.

## What remains in place

The migration preserves the tenant-owned state in the existing repository when you keep these paths:

| Keep | Why it matters |
| --- | --- |
| `EntraOpsConfig.json` | Holds your tenant, application client ID, workflow triggers, integration, and protection settings. |
| `PrivilegedEAM/` and its Git history | Contains collected privileged-access data and remains the source for reports. The Privilege History report is generated by walking the Git commits that changed `PrivilegedEAM/`, so historical comparisons live in your commit history, not in `Reports/`. |
| `Classification/<TenantName>/` | Contains tenant-specific generated classification parameters and locally maintained overwrite files. |
| `TenantGovernance/Snapshots/` | Contains tenant governance snapshot files and their manifests, used for historical comparisons. Present when Tenant Governance collection is enabled. |

Do not delete `PrivilegedEAM/`, tenant-specific `Classification/` content, `TenantGovernance/Snapshots/`,
or `EntraOpsConfig.json`. They are not replaced by an EntraOps update.

Two paths look like tenant state but are not: the `Reports/` folder contains the shipped report apps and
**is** replaced during the update - generated report data under `Reports/*/data/` is excluded from Git
and regenerated by the `Push-EntraOpsPrivilegedReporting` workflow. The values in `.github/workflows`
are regenerated from your existing config after the current workflow files are introduced (step 2).

## 1. Protect the current deployment

Work from a clean branch in the existing private repository. Confirm its default branch is still the
one used by the federated credential, usually `main`.

```powershell
git status
git switch main
git pull --ff-only
git switch -c upgrade/entraops-current
Copy-Item EntraOpsConfig.json EntraOpsConfig.before-migration.json
```

Keep the backup local or in your approved secret/configuration backup location. `EntraOpsConfig.json`
contains tenant and application information, so do not publish it outside the private repository.

## 2. Update EntraOps files in the existing repository

Import the module from the existing checkout, then run `Update-EntraOps` **twice**. The first run
executes the 0.x version of the cmdlet, which has a smaller update scope: it refreshes the module
folder (`EntraOps/`) itself but cannot update `Docs/`, `Reports/`, or `Tests/`, and it **replaces the
entire `.github/` folder - including `.github/workflows` - with the upstream files**. Re-import the
updated module and run it a second time so the current update scope applies: it then also updates
`Docs/`, `Reports/`, `Tests/`, actions, and trusted update scripts. Workflow definitions are excluded
from the current default target set; the first 0.x run has already introduced the upstream workflow
files during this migration. Both versions preserve
your tenant data and classification output because `PrivilegedEAM/`, `Classification/`,
`TenantGovernance/`, and `EntraOpsConfig.json` are not in their update lists.

```powershell
Import-Module ./EntraOps -Force
Update-EntraOps -ConfigFile ./EntraOpsConfig.json
Import-Module ./EntraOps -Force
Update-EntraOps -ConfigFile ./EntraOpsConfig.json
```

Because the first run replaces `.github/workflows` with upstream templates, review `git diff .github`
and restore any organization-specific workflow changes from the diff. Apply supported values from the
retained `EntraOpsConfig.json` with the command in step 4. Review the remaining changed files before
committing.
If the update reports a merge conflict, preserve your locally maintained configuration and
tenant-specific classification files, then resolve the source file against the current EntraOps
version.

## 3. Review the updated GitHub workflows

The current `Update-EntraOps` excludes `.github/workflows` from its default target set. This prevents
the automated updater from failing when its built-in `GITHUB_TOKEN` attempts to publish workflow-file
changes. To refresh workflows manually from the configured upstream ref, run:

```powershell
Import-Module ./EntraOps -Force
Update-EntraOps -ConfigFile ./EntraOpsConfig.json -RunBrowserTests `
  -TargetUpdateFolders @('./.github/actions', './.github/scripts', './.github/workflows')
```

Changed workflow templates require candidate validation even when `ValidationFrequency` is `Never`,
and supported tenant values are automatically reapplied from the existing `EntraOpsConfig.json`.
Review the resulting workflow diff before committing with your normal GitHub user credentials.

To opt into automated workflow updates instead, install a dedicated GitHub App on the deployment
repository with Contents, Workflows, Pull requests, and Commit statuses write permissions. Configure
the `EntraOpsUpdateAppClientId` repository variable and `EntraOpsUpdateAppPrivateKey` repository
secret, then add `./.github/workflows` to `AutomatedEntraOpsUpdate.TargetUpdateFolders` while retaining
`./.github/actions` and `./.github/scripts`. See the
[core update documentation](../../core/index.html#update-entraops-powershell-module-and-cicd) for the complete setup
and security behavior.

## 4. Keep and apply your existing EntraOpsConfig.json

Retain your current `EntraOpsConfig.json`; do not replace it with a newly generated file. Add newly
documented settings only when you need their feature. The [Configuration Wizard](../../configuration/index.html)
can import the existing file and export an expanded version. It merges edited fields into the imported
document so unknown extension properties and newer settings are retained; still review the semantic
diff before replacing production configuration.

A configuration created before the contracted update mechanism has no `AutomatedEntraOpsUpdate.Repository`
or `TargetUpdateFolders` keys. The updater then resolves the built-in defaults (`EntraOps`,
`main`, and the default target list) and logs a warning naming the missing keys. Add them explicitly to
make the update source reviewable in your configuration. Existing explicit automation and schedule
values remain unchanged during migration; a missing `PublicationMode` resolves to `PullRequest`.
Automated updates stay disabled unless `ApplyAutomatedEntraOpsUpdate` is explicitly `true`. Use
`"Repository": "EntraOps-Insiders"` only with the `EntraOpsUpdatePat` secret in place, and enable
"Allow GitHub Actions to create and approve pull requests" in the repository before turning on
`PullRequest` publication:

```json
"AutomatedEntraOpsUpdate": {
  "ApplyAutomatedEntraOpsUpdate": false,
  "UpdateScheduledTrigger": false,
  "UpdateScheduledCron": "0 9 * * 3",
  "Repository": "EntraOps",
  "Branch": "main",
  "PublicationMode": "PullRequest",
  "ValidationFrequency": "OnChange",
  "RunBrowserTests": true,
  "TargetUpdateFolders": [
    "./.github/actions", "./.github/agents", "./.github/scripts", "./Docs", "./EntraOps",
    "./Parsers", "./Queries", "./Reports", "./Samples", "./Tests", "./Workbooks",
    "./package.json", "./package-lock.json", "./playwright.config.mjs", "./CHANGELOG.md",
    "./EntraOpsUpdateContract.json"
  ]
}
```

Every entry in `TargetUpdateFolders` must be listed in the source repository's
`EntraOpsUpdateContract.json`; the update is rejected before any file is changed otherwise.

Apply the retained config to the newly copied workflow files:

```powershell
Import-Module ./EntraOps -Force
Update-EntraOpsRequiredWorkflowParameters -ConfigFile ./EntraOpsConfig.json
```

This writes the tenant, client ID, workflow triggers, and enabled feature settings into
`.github/workflows`. It is the required step after refreshing workflow files and whenever you change
workflow-related configuration.

## 5. Review identity and permissions

Keep the existing EntraOps application and federated credential. Do not create a second application
with the new-deployment template flow. When the upgraded configuration enables a feature requiring
additional permissions, grant only the missing permissions to the existing service principal:

```powershell
New-EntraOpsWorkloadIdentity -AppDisplayName "<existing-app-display-name>" `
  -ExistingSpObjectId "<existing-service-principal-object-id>" `
  -ConfigFile ./EntraOpsConfig.json
```

Review the command output and ignore only conflicts for permissions or roles that are already present.
Use the existing federated credential branch and repository identity; recreate it only when the
repository or default branch changed.

## 6. Commit and verify the in-place upgrade

Commit the EntraOps update, workflow refresh, and configuration changes together. Stage the whole
working tree rather than a fixed file list: the update also adds root files (`EntraOpsUpdateContract.json`,
`package.json`, `.EntraOpsUpdateManifest.json`) and removes files that no longer ship, and the same
`git add --all` is what the automated `Update-EntraOps` workflow commits. Generated report data and
`TmpUpdate/` are excluded by `.gitignore`. The negative pathspec keeps the step 1 backup out of the
commit; drop it only if that backup is your intended version-controlled copy.

```powershell
git add --all -- . ':!EntraOpsConfig.before-migration.json'
git status
git commit -m "Upgrade EntraOps deployment"
git push --set-upstream origin upgrade/entraops-current
```

Merge through your normal review process. In GitHub Actions, run `Pull-EntraOpsPrivilegedEAM` manually
once, then confirm OIDC authentication succeeds and the run updates the existing `PrivilegedEAM/`
paths. Verify any enabled `Push-EntraOpsPrivilegedEAM`, `Push-EntraOpsPrivilegedReporting`,
`Pull-EntraOpsTenantGovernance`, and `Update-EntraOps` workflows afterwards.

## Upgrade from EntraOps 1.0 to 1.1 {#upgrade-from-1-0}

A 1.0 deployment is upgraded in place like a 0.x deployment: keep `EntraOpsConfig.json`, `PrivilegedEAM/`,
`Classification/<TenantName>/` and `TenantGovernance/Snapshots/`, and work on a branch of the existing
repository (see [1. Protect the current deployment](#1-protect-the-current-deployment)).

**1. Update the repository including the workflow definitions.** The scheduled `Update-EntraOps` workflow and
the default update targets don't include `./.github/workflows`, so a 1.0 deployment keeps its 1.0 workflows.
1.1 reworks them, e.g. `Push-EntraOpsPrivilegedReporting` runs the report tests in a separate job without write
permissions and Azure sign-in, and only the release job can write to the repository. Run the 1.0 cmdlet once,
re-import the module, and run the 1.1 cmdlet with the workflow definitions as additional target; it re-applies
the values of your `EntraOpsConfig.json` to the workflows:

```powershell
Import-Module ./EntraOps -Force
Update-EntraOps -ConfigFile ./EntraOpsConfig.json
Import-Module ./EntraOps -Force
Update-EntraOps -ConfigFile ./EntraOpsConfig.json -TargetUpdateFolders @(
    "./.github/actions", "./.github/agents", "./.github/scripts", "./.github/workflows",
    "./Docs", "./EntraOps", "./Parsers", "./Queries", "./Reports", "./Samples", "./Tests", "./Workbooks",
    "./package.json", "./package-lock.json", "./playwright.config.mjs", "./CHANGELOG.md", "./EntraOpsUpdateContract.json")
```

The second run re-applies the values of your `EntraOpsConfig.json` to the new workflows
(`Update-EntraOpsRequiredWorkflowParameters`). Review `git diff .github/workflows`: changes you made to the 1.0
workflows yourself (e.g. additional steps, runner labels or environments) aren't kept. Restore them, then run
`Update-EntraOpsRequiredWorkflowParameters -ConfigFile ./EntraOpsConfig.json` again so the configured values are
applied. Push with credentials that may change workflows (e.g. a token with the `workflow` scope), then start a new
PowerShell session.

**2. Keep your configuration.** Don't replace `EntraOpsConfig.json` with a newly generated file. 1.0
configuration files keep working; the new settings are optional:

- `AlternateObjectTierLevelAttributes.<User|ServicePrincipal|Group>.Enabled` replaces the former top-level
  `Enabled` (still honored for users and service principals). The Configuration Wizard converts it on import.
- `CustomSecurityAttributes.Enabled` and `ObjectClassificationFile` select the
  [classification sources](../../core/index.html#classification-sources).
- `ServiceEM` and `AzureDevOpsServiceConnection` are only needed for Service EM and Azure DevOps.
- `ConfigurationAnalyzer.TimeRangeInDays` (default 365) and `ConfigurationAnalyzer.SnapshotInterval` (default
  `P1W`) now bound the Configuration Analyzer dataset also when they are missing, and a stale Tenant Governance
  snapshot only warns by default (`ConfigurationAnalyzer.StaleTenantGovernanceSnapshotAction`).

**3. Redeploy the parsers and WatchLists** when you use the Microsoft Sentinel integration (WatchLists parser
0.5, Custom Table parser 0.4). `Save-EntraOpsPrivilegedEAMInsightsCustomTable` now writes a completion marker
record per RBAC system (`ObjectType` `EntraOpsIngestionRun`) to `PrivilegedEAM_CL`: queries that read the table
directly instead of through the parser must exclude these records.

**4. Review changed behavior.**

- `Connect-EntraOps` loads `EntraOpsConfig.json` from the current folder, otherwise from the EntraOps
  [working folder](../index.html#working-folder), when `-ConfigFilePath` isn't passed. A configuration set in the
  session before is removed when no file is found.
- The warning `IntuneDeviceScopeDesignatedTierGap` is now `IntuneDeviceScopeSelectionGap`; update alert rules or
  log filters that match the former name.
- `Test-EntraOpsGeneratedArtifacts` fails, instead of warning, when a `Classification`, `MatchedActions` or
  `ScopedObjects` collection of the export is stored as a single value.

**5. Verify.** The workload identity needs no new permissions for the 1.0 features. Run
`Pull-EntraOpsPrivilegedEAM` manually and check that `Push-EntraOpsPrivilegedEAM` and
`Push-EntraOpsPrivilegedReporting` follow it, as in [6. Commit and verify the in-place upgrade](#6-commit-and-verify-the-in-place-upgrade).

## Do not use the new deployment path

For an existing EntraOps 0.x GitHub deployment, skip **Get Started -> Create your repository from
this template**, the new-repository clone step, and the new workload-identity creation step. Those
steps are for first-time deployments only. Migration keeps the existing private repository, Git
history, `PrivilegedEAM` data, tenant classification, `EntraOpsConfig.json`, application, and
federated credential.
